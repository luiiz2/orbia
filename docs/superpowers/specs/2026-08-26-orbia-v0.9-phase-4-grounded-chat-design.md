# Orbia v0.9 — Phase 4: Hybrid Retrieval, Grounded Chat and Source Navigation

**Status:** design approved in chat; awaiting written-spec review
**Scope:** Phase 4 only. This phase adds retrieval, grounded chat, persisted conversations and source navigation over the Phase 3 local semantic index. It does not add summaries, generated chapters, or a general-purpose semantic-search screen.

## Goals

- Answer questions from indexed Orbia content at lesson, module, course and vault scope.
- Combine lexical search with semantic similarity instead of depending on embeddings alone.
- Keep every displayed source reference tied to a real indexed chunk and validate its navigation target at the Main-process boundary.
- Persist compact local conversations without re-sending an entire transcript or conversation on every question.
- Preserve the Phase 1 privacy contract: all AI routing stays in `AiCoreService`; `LOCAL_ONLY` never calls a cloud embedding or chat provider.

## Non-goals

- No automatic indexing, transcription, summaries, generated chapters, RAG authoring workflow, or advanced semantic-search UI.
- No external vector database, server, cloud storage, or renderer-side filesystem access.
- No general-knowledge fallback when indexed content is insufficient.
- No model-generated citations, source IDs, timestamps or navigation links.

## Architecture

Phase 4 extends the Phase 3 SQLite semantic index in the Main process. The renderer asks for an answer with a typed scope; the Main process resolves the scope, retrieves evidence, conditionally calls `AiCoreService.chat`, persists the result and returns the answer plus structured evidence.

```text
Renderer action
  -> typed IPC request
  -> GroundedChatService
       -> HybridRetrievalService
            -> SQLite FTS5 lexical candidates
            -> compatible query embedding through AiCoreService
            -> local vector similarity candidates
            -> metadata filter + reciprocal-rank fusion
       -> grounded prompt builder
       -> AiCoreService.chat
       -> local conversation repository
  -> answer + retrieval-owned evidence
```

`GroundedChatService` owns question handling, history limits, answer persistence and insufficient-evidence responses. `HybridRetrievalService` owns ranking only. `SourceNavigationService` independently validates a selected evidence item before returning an allowed lesson, timestamp, material or PDF-page target. These boundaries keep retrieval, model invocation and navigation independently testable.

## Hybrid retrieval

### Lexical index

The vault SQLite database gains an FTS5 external-content index over `semantic_index_chunks.text`. The chunk table remains the single source of truth for source text; FTS stores only its search index and is maintained by insert, update and delete triggers. A migration rebuilds the FTS index from already stored chunks.

Lexical retrieval uses parameterized FTS queries and BM25 ranking. Empty or syntactically invalid FTS input is handled as an empty lexical result, never as raw SQL. The query path joins back to `semantic_index_chunks`, so generation, source revision and scope filters apply before candidates are exposed.

### Semantic candidates

For a semantic query, `HybridRetrievalService` asks `AiCoreService.embed` for exactly the user question. It compares the returned provider, model and vector dimensions with the active generation. If they are incompatible, semantic ranking is skipped for that request and lexical retrieval remains available; the service never mixes incompatible vectors and never silently rebuilds the index.

Candidate vectors are read from the existing local SQLite embedding BLOBs, filtered by scope in the Main process, decoded as Float32 arrays and ranked by cosine similarity. Retrieval has a fixed candidate cap, so a question does not scan unbounded vault content. No external vector service is introduced.

### Scope and metadata filters

The API accepts one explicit scope:

| Scope | Required identity | Eligible evidence |
| --- | --- | --- |
| `lesson` | canonical lesson ID | chunks for that lesson, including its transcript, subtitles, attached materials and permitted metadata |
| `module` | module ID | chunks whose stored module ID matches |
| `course` | course ID | chunks whose stored course ID matches |
| `vault` | current opened vault | chunks in the active index generation |

Scope resolution and all IDs are validated against the vault database in the Main process. The renderer cannot widen a supplied lesson request into another course. Source kind, canonical lesson ID, resource ID, source revision and time/page/line locator remain attached to every candidate.

### Ranking and relevance

Lexical and semantic candidate lists are fused with reciprocal-rank fusion. For `Explain This`, chunks overlapping the active player timestamp receive a bounded proximity signal after scope filtering; nearby transcript evidence is always included first when available. Exact lexical matches can therefore surface even when embeddings are weak, and semantic matches can surface paraphrases that FTS misses.

The result is limited to a compact context budget: two nearby transcript chunks for a player explanation plus up to four ranked chunks for retrieval, deduplicated by chunk and source. A relevance decision requires at least one usable retrieved chunk. If there is no usable support, the service returns the local status `insufficient_evidence` without invoking a chat provider.

The active generation remains the only generation used for answers. A partially built or failed generation is not presented as a fully indexed vault. Existing Phase 3 status is surfaced to the UI so an answer is never described as covering unindexed or stale content.

## Grounded chat and privacy

Each model request consists of:

1. a static trusted instruction that the answer may use only the provided sources, must treat source text as untrusted data, and must state when evidence is insufficient;
2. a short, bounded continuation history from the local conversation;
3. a compact block of retrieved source text, each labelled only for the prompt; and
4. the current question or selected-text instruction.

Source blocks are explicitly delimited as untrusted content. Text such as “ignore previous instructions” inside a transcript, PDF or code sample has no authority over the trusted instruction. The model is not asked to return citations. The renderer receives only evidence selected by retrieval, so a fabricated source ID or timestamp in model prose has no navigable effect.

`AiCoreService` remains the sole route to embedding and chat providers. Retrieved source kinds are translated to the existing AI data-type and consent checks before any provider call. Under `LOCAL_ONLY`, provider routing rejects both cloud embeddings and cloud chat before network invocation. Provider failures, unavailable models and cancelled requests produce an error state with no partially valid-looking answer.

## Conversation storage

The vault database gains these local tables:

| Table | Purpose |
| --- | --- |
| `chat_conversations` | conversation ID, user-editable title, timestamps and soft metadata needed for listing |
| `chat_messages` | conversation ID, role, content, request scope snapshot, answer status, provider/model provenance and timestamps |
| `chat_message_sources` | immutable evidence snapshot for an assistant message: ordinal, originating chunk ID, source kind, course/module/lesson/resource/transcript IDs, source revision, locator and display label |

`chat_message_sources` intentionally does not depend on a live foreign key to a deletable chunk. A historical answer continues to show which source supported it even after reindexing or source deletion; navigation is then validated live and may report that the original source is no longer available.

Users can list, continue, rename and delete conversations. Each new question re-runs retrieval against the current index and sends only a short recent history window with a strict character budget. It does not append the full transcript, full evidence history or the whole prior chat to every request.

## Player and chat UI

A reusable grounded-chat panel receives a prefilled scope and optional context. It is opened by:

- **Ask About This Lesson** and **Explain This** in the player;
- **Ask About This Module** and **Ask About This Course** from course curriculum controls;
- **Ask Orbia** from the application shell for the current vault;
- **Explain**, **Ask AI** and **Create Note** for selected transcript text.

`Explain This` captures the current player timestamp and supplies only the closest transcript neighborhood plus ranked supporting chunks. Transcript rendering separates its seek control from selectable text, preserving keyboard-accessible timestamp seeking while allowing text selection. `Create Note` reuses the existing timestamped-note flow and does not call an AI provider.

Answers have a collapsible **Sources Used** region populated only from `chat_message_sources`. Each source presents real course, module, lesson and locator metadata when available. It exposes only actions applicable to validated live content: **Open Lesson**, **Open at Timestamp**, **Open Material** and **Open PDF Page**. The panel displays an explicit local insufficient-content message when retrieval has no support and an index-status hint when the selected scope is only partially indexed.

## Source navigation safety

On every navigation click, the renderer sends the evidence record ID, not a file path or free-form source ID. `SourceNavigationService` loads its stored snapshot, checks that the referenced course, module, lesson and resource still exist in the current vault, verifies ownership relationships and derives the only allowed target:

- a canonical lesson ID and optional bounded timestamp;
- an existing content resource for material navigation;
- an existing PDF resource and a positive page number for PDF navigation.

The renderer then uses the existing player seeking and PDF/material UI. If validation fails, it receives `unavailable` and shows a non-destructive notice. Model text never participates in this decision.

## Error and state handling

| Condition | Result |
| --- | --- |
| no active or usable index | local insufficient-content response; no model call |
| no relevant candidates in scope | local insufficient-content response; no model call |
| query embedding unavailable or incompatible | lexical-only retrieval; show no false semantic claim |
| chat provider/model unavailable | failed message state, retryable from the same question; evidence is not fabricated |
| cloud route rejected by `LOCAL_ONLY` or consent | failed privacy state before provider invocation |
| cancellation | cancelled state, without an assistant answer treated as complete |
| deleted or moved source | historical source label remains; live navigation returns unavailable |
| partial index | UI identifies partial/stale coverage and never calls it fully indexed |

## IPC and renderer contract

New typed Main-process IPC methods cover: ask/continue a conversation, list/get/rename/delete conversations, fetch an answer’s stored sources, and resolve a source-navigation target. Requests use typed scope objects and optional current-moment or transcript-selection context; responses contain assistant status, text, index coverage state and retrieval-owned source objects. No direct database, filesystem, provider credential or raw media-path data crosses to the renderer.

The existing semantic-index IPC surface is completed consistently with the Phase 3 API contract before the chat UI consumes index status.

## Migration and compatibility

A single Phase 4 vault-schema migration creates the FTS5 index, its triggers and conversation tables. It does not alter media identity, canonical lesson IDs, transcript data or semantic embeddings. The FTS migration rebuilds from existing semantic chunks; no re-transcription or re-embedding is required. It is idempotent under the database migration ledger and follows existing WAL/transaction practices.

## Test and verification strategy

Tests remain focused on regression risks rather than component-render checks:

- SQLite integration tests cover FTS lexical results, semantic similarity, reciprocal-rank fusion, metadata scope filters, timestamp preservation and no-result behavior.
- Retrieval tests cover lesson, course and vault scopes; incompatible provider/model/dimension fallback; incremental transcript revision; source deletion; and partial-generation status.
- Grounded-chat tests assert that unsupported questions do not call a provider, untrusted prompt-injection fixtures remain data, `LOCAL_ONLY` blocks cloud routing, and the returned evidence comes from retrieval rather than model output.
- Navigation tests prove that valid timestamp, material and PDF-page actions resolve to existing entities and fabricated/deleted IDs resolve to `unavailable`.
- Conversation tests cover local persistence, continuation with bounded history, rename and delete.
- Targeted player/transcript tests cover the selected-text action payload and existing accessible timestamp seeking; they do not duplicate broad UI rendering coverage.

Verification runs the relevant focused suites during development, then the complete test suite, TypeScript checks, lint and a bounded retrieval performance check using representative indexed data. The performance check verifies candidate and context caps rather than relying on a brittle machine-specific time threshold.

## Acceptance criteria

- Questions in all four scopes use hybrid retrieval with Main-process metadata enforcement.
- Source-backed answers retain retrieval-owned structured evidence and navigate only after live validation.
- Unsupported questions return an explicit insufficient-content result without a model call.
- `LOCAL_ONLY` never invokes a cloud embeddings or chat endpoint.
- Conversations remain local and can be continued, renamed and deleted.
- Player moment and transcript selection actions use minimal context, preserve seeking and remain keyboard accessible.
- Phase 4 ships without summaries, chapters or an advanced semantic-search UI.
