# Orbia v0.9 Phase 3 — Content Extraction, Chunking, Embeddings, and Semantic Index

## Scope

Implement the local, versioned semantic-index pipeline for text-bearing Orbia content:

1. extract supported source text;
2. create structured chunks with recoverable provenance;
3. route chunk batches through the existing Phase 1 embedding service;
4. persist vectors and index metadata in the vault SQLite database;
5. run lesson/course/vault/selected-content indexing through the existing persistent background queue;
6. expose status, progress, controls, settings, storage metrics, and rebuild through typed IPC and minimal UI.

This phase does not implement AI Chat, RAG retrieval, semantic search, summaries, generated chapters, OCR for scanned PDFs, or automatic full-library indexing.

## Existing infrastructure to preserve

- `AiCoreService.embed()` remains the only application entry point for embeddings. It already performs route selection, model discovery, capability validation, fallback, privacy checks, and cloud-consent enforcement.
- `OptimizationQueueService` and `OptimizationWorkerService` remain the only durable background-job system. Semantic indexing adds a job discriminator/payload to the same SQLite queue.
- `ResourceManagerService` remains the resource gate. Playback keeps priority through its existing player-activity/battery policy.
- `DatabaseService` remains the vault SQLite owner, including WAL, foreign keys, migrations, and vault lifecycle.
- Canonical course/module/lesson/resource IDs remain the identity of content. Physical paths are only extraction locations.
- Existing transcript storage and current-transcript selection are reused. Rebuild reads persisted transcripts and never retranscribes.
- Existing subtitle resources and `mupdf` dependency are reused. No external vector server or required new package is introduced.

## Source support and extraction

### Source precedence

For each lesson, index at most one effective transcript text source for the same logical content:

1. current completed transcript, including its timestamped segments;
2. a valid matching subtitle resource when no current transcript exists;
3. supported lesson/module content resources (`pdf`, Markdown, TXT, source code, and text documents that are explicitly classified as text-bearing).

Existing transcript/subtitle text is not duplicated as a second generic resource. A subtitle remains a usable source when a transcript is absent; it is not retranscribed or re-extracted through a provider.

The extractor also emits compact metadata chunks for the course, module, and lesson relationship when a selected scope contains those entities. Metadata is useful index content but carries ordinary course/lesson provenance and the same generation version.

### Formats

- Transcripts: current transcript segments from `transcripts`/`transcript_segments`.
- Subtitles: existing SRT/WebVTT parser and subtitle resource identity.
- PDF: `mupdf` text extraction page by page using structured text. Empty pages are skipped. Scanned-image OCR is intentionally unsupported in this phase.
- Markdown/TXT: UTF-8 text read from the registered resource path.
- Source code: UTF-8 text read from the registered resource path; language is derived from the extension and filename/line range are stored.
- Other binary media: skipped with a source-level unsupported/empty result; no guessed text is indexed.

Every file read validates that the path is the registered database path for the selected content and records a source revision. A missing or unreadable file does not produce an apparently valid chunk.

## Chunk model

The logical chunk is the unit sent to the embedding provider and stored in SQLite. Each chunk includes:

- stable chunk ID within an index generation;
- generation ID;
- source kind (`transcript`, `subtitle`, `pdf`, `markdown`, `text`, `code`, `note`, `metadata`);
- exact source ID (`transcript:<id>`, `resource:<id>`, `note:<id>`, or deterministic metadata identity);
- canonical `courseId`, optional `moduleId`, optional `lessonId`;
- source revision and content revision;
- normalized text stored once for the chunk;
- structured locator JSON containing page, line range, filename/language, or transcript start/end as applicable;
- optional transcript `start`/`end` columns for direct seeking and future retrieval consumers.

The chunking version is `semantic-chunk-v1`. Generic text is first split on paragraph and sentence boundaries, then packed up to a conservative safety limit without splitting a sentence unless one unusually long sentence must be bounded. Transcript chunks group contiguous segments at sentence boundaries and use the first segment start and last segment end. Code chunks group meaningful blank-line blocks and retain inclusive line ranges; a single oversized block is bounded by line boundaries. Empty/whitespace-only chunks are discarded.

The source identity tuple is `(sourceKind, sourceId, sourceRevision, contentRevision)`. Replacement of a source deletes only rows matching that source identity in the active generation before inserting its new chunks. A transcript revision includes the transcript record ID/version so a new retranscription reindexes even if the media revision is unchanged.

## Versioned local index

Use one logical semantic index per vault with generations:

### `semantic_index_generations`

Stores one immutable configuration for a generation:

- `id`, `status`, `created_at`, `completed_at`;
- embedding `provider_id`, `model_id`, `dimensions`;
- `chunking_version`;
- counts for discovered, extracted, embedded, failed, and indexed chunks;
- byte metrics for stored text and vectors;
- error summary;
- `is_current`.

Allowed statuses are `building`, `partial`, `completed`, `failed`, `cancelled`. Only a completed generation becomes current. A partial/failed/cancelled rebuild never replaces a working current generation.

### `semantic_index_chunks`

Stores structured chunk text and provenance. Foreign keys cascade from generations and canonical content where safe; the explicit `source_kind`/`source_id` fields remain authoritative for exact provenance because transcript versions and resource records have different identities.

### `semantic_index_embeddings`

Stores one vector per chunk as a `Float32Array` byte BLOB, plus provider/model/dimension fields copied for validation. A vector is written only after it is finite, non-empty, and has exactly the generation dimension. There is no mixed-dimension generation.

### `semantic_index_settings`

Stores vault indexing settings. `include_notes` defaults to false. Notes are never indexed unless explicitly enabled. No source text is copied into settings or queue payloads.

The current generation is used for indexing updates. A model/provider/dimension/chunking change creates a new generation when a rebuild is requested; it does not silently mix vectors and does not delete the current generation before the replacement completes.

## Embedding routing and privacy

`SemanticIndexService` sends bounded batches of chunk text to `AiCoreService.embed({ input, dataTypes, cloudConsent })`. Data categories are derived from the batch source kinds (`transcript`, `notes`, `pdf`, `materials`, `course_name`) and deduplicated.

`LOCAL_ONLY` is enforced by the existing AI routing layer. The semantic index does not call providers directly and cannot override privacy mode. Cloud embedding requires both the configured allowed data types and explicit request consent. A provider/model error fails the affected generation or source update without publishing invalid vectors.

## Scope and incremental behavior

The service accepts exactly one scope:

- `lesson` with one lesson ID;
- `course` with one course ID;
- `vault` with all eligible registered content;
- `selected` with explicit lesson/resource/note IDs.

Vault indexing is explicit. Enabling notes only affects future requested indexing; it does not automatically enqueue the vault.

Incremental source replacement is available for a lesson, resource, or note. It extracts and embeds only that source, replacing rows for that source in the active generation. When a source disappears, its rows are removed from the active generation; the source text is not retained as an orphan. If no current generation exists, the service creates a generation before an incremental request.

## Durable jobs and lifecycle

Semantic index requests use the existing `optimization_queue` row with `job_type = 'semantic_index'` and a JSON payload containing scope, IDs, rebuild flag, note setting, and cloud consent. The worker dispatches it to `SemanticIndexService.processJob()` under the same `ResourceManagerService` gate.

The worker persists progress after each source/batch and supports queued pause/resume, cancellation, retry, and startup recovery. Active interrupted indexing is reset to queued; an incomplete generation remains `partial`/`failed` and cannot become current. Cancellation checks occur before each source and embedding batch. Playback pressure prevents new work or yields between safe source boundaries according to existing resource settings.

Indexing status is calculated from persisted counts. A generation with 40% success is `partial`, not `completed`.

## IPC and UI

Add a typed `semanticIndex` API for:

- enqueueing a scope or rebuild;
- incremental source update/removal;
- reading current generation/status/metrics;
- reading queue entries;
- pause/resume/cancel/retry.

Add a compact Settings card for notes permission, current index metrics, and explicit vault rebuild/index actions. Add a course-level indexing action where existing course actions live. This phase does not add a query box or search-results UI. Renderer code only uses the preload API; filesystem and SQLite remain in Main.

## Error semantics

Errors are persisted without secrets or full provider responses. Distinguish unavailable source, unsupported format, provider unavailable/model missing, privacy blocked, embedding failure, cancellation, and partial completion. A failed source is counted and reported; its old active-generation rows remain until a successful replacement or explicit source removal, unless the whole new generation is being built.

## Acceptance criteria

- Supported transcripts, subtitles, textual PDFs, Markdown, TXT, code, opt-in notes, and metadata produce structured, provenance-complete chunks.
- Transcript timestamps, source revision, course/module/lesson IDs, PDF pages, and code filename/line ranges survive chunking and persistence.
- Local and cloud embedding routes use Phase 1 AI routing; `LOCAL_ONLY` never reaches a cloud embedding provider.
- SQLite generations prevent provider/model/dimension/chunking mixing and publish atomically only on complete success.
- Lesson/course/vault/selected scopes enqueue through the existing durable queue and expose pause/resume/cancel/retry/progress.
- Incremental changes replace only affected source rows; deletions remove only the deleted source; rebuild reuses stored transcripts.
- Partial state and storage metrics are accurate.
- Tests cover all requested high-risk behavior without adding trivial coverage tests.
- Tests, typecheck, lint, and relevant build/performance checks pass.
