# Orbia v0.9 Phase 2 — Transcription Engine, Storage, and Player UI

## Scope

Implement only on-demand and opt-in automatic transcription, transcript persistence, and transcript playback UI.

Explicitly out of scope: embeddings, RAG, semantic search, summaries, chapters, flashcard generation, and any automatic transcription of the existing library by default.

The implementation must preserve the existing v0.7/v0.8 persistent optimization queue, worker lifecycle, resource manager, canonical lesson IDs, media source abstraction, subtitle handling, and player seeking.

## Current architecture to preserve

- `OptimizationQueueService` is the existing persistent job store and recovery point.
- `OptimizationWorkerService` owns the long-running main-process loop and abort signal.
- `ResourceManagerService` controls whether background work may run while playback is active or the machine is on battery.
- `MediaSourceInput` and FFmpeg provide the existing media access and processing path.
- `DatabaseService` owns vault SQLite migrations and transactional persistence.
- `AiCoreService` owns provider routing, capability checks, privacy, and cloud-data consent.
- `PlayerView`, `usePlayerStore`, and `usePlayer` already expose current time and seeking.

## Design decisions

### 1. One durable job system

Extend the existing `optimization_queue` schema and service with a `job_type` discriminator and transcription payload fields. Keep optimizer-facing types and APIs compatible. Transcription jobs are selected by the same worker loop, and both job types use the same resource gate and lifecycle controls.

The worker dispatches by `job_type`. Existing optimization behavior remains in its current processor; transcription gets a bounded processor that uses the existing abort signal and resource manager.

Persist enough information to recover safely after renderer reload, window close, application restart, or recoverable interruption. Active transcription jobs are reset to queued on startup; temporary audio and partial provider output are removed. A partial result is never published as a completed transcript.

### 2. Transcript persistence

Add a vault migration with:

- `transcripts`: versioned transcript records keyed by canonical `lesson_id`, with `language`, `provider`, `model`, `created_at`, `source_revision`, `settings_json`, `status`, `is_current`, and sanitized error information.
- `transcript_segments`: normalized timestamped segments keyed by transcript ID, with sequence, start, end, and text.

Keep successful historical versions. A new version becomes current only inside a transaction after all segments have been validated and persisted. Failed, cancelled, or partial jobs do not replace the current version.

The source revision is resolved from existing stable source metadata (revision/checksum/fingerprint/content hash, with a deterministic file metadata fallback) and never from the physical path. Moving or optimizing a media file therefore preserves transcript identity through the canonical lesson ID.

### 3. Provider contract

Extend the AI provider adapter/core with a normalized `transcribe` operation and use the existing `TRANSCRIPTION` capability and routing/privacy checks.

Implement verbose timestamped transcription for OpenAI-compatible providers, including OpenAI-compatible local endpoints and the configured OpenAI cloud endpoint. Support explicit language and auto-detect. Use FFmpeg to create the provider input from the existing media source abstraction.

Providers without a real transcription endpoint return a clear unsupported-capability error. No provider response is fabricated or converted into a valid-looking transcript when segments are missing or incomplete.

### 4. Existing subtitle reuse

Before creating a provider job, inspect lesson subtitle resources. Parse valid SRT/WebVTT into the same segment model. Expose reuse as an explicit action and allow the UI to offer reuse before provider transcription. Reused subtitles carry provenance identifying the source as an existing subtitle and retain the source revision.

### 5. Batch and automatic scheduling

Expose lesson, module, and course enqueue operations. Batch operations deduplicate active jobs by lesson ID. The default is on-demand.

Add opt-in settings for:

- vault-level automatic transcription of newly imported/synced lessons;
- course-level automatic transcription of newly imported lessons.

Existing lessons are not bulk-enqueued when a setting is enabled. New automatic jobs still pass through the shared queue and resource gate.

### 6. Retranscription and errors

`Retranscribe` always creates a new transcript version and does not automatically run merely because provider/model configuration changed. Current content remains available until successful replacement.

Represent provider unavailable, model missing, unsupported media, source unavailable, provider failure, cancellation, and recoverable interruption as explicit job/transcript states. Retry requeues the same logical request with a clean progress state. Partial provider output stays temporary and is discarded on failure/cancellation.

### 7. Player UI

Add a `Transcript` tab to the existing player side panel. The panel loads the current lesson transcript and exposes reuse/transcribe/retranscribe actions, language selection, status/error feedback, timestamped segments, current-segment highlighting, click-to-seek, text search with match highlighting, and keyboard-accessible segment controls.

Wire playback activity from the renderer to the existing main-process resource manager so background transcription pauses or yields while the user is watching according to existing optimization settings.

## Implementation sequence

1. Add focused domain types and failing tests for transcript records, segments, source revision, and job payload/state rules.
2. Add the database migration and repository/service methods for transcript versions, segments, settings, and atomic current-version replacement.
3. Generalize the existing queue row/service with the smallest compatible `job_type`/payload extension and add tests for deduplication, batches, retry, cancellation, recovery, and worker restart.
4. Extend AI provider/core contracts and implement timestamped transcription for the supported HTTP providers. Add tests for language/autodetect, provider/model failures, malformed/partial responses, and capability/privacy routing.
5. Implement subtitle parsing/reuse through the existing subtitle utilities and source revision resolver.
6. Implement the transcription worker processor, FFmpeg input handling, cancellation, cleanup, persistence, and auto-transcription enqueue hooks.
7. Add typed main IPC and preload APIs, including progress subscription and player-activity signaling.
8. Add renderer transcript store/panel and integrate it into `PlayerView` without changing unrelated player behavior.
9. Run focused tests after each slice, then the full suite, typecheck, lint, and build. Inspect the complete diff and verify no semantic-indexing code was added.

## Verification criteria

- lesson, module, and course requests create the expected durable jobs;
- subtitle reuse produces timestamped segments without provider transcription;
- language selection and auto-detect reach the provider contract;
- pause/resume, retry, cancellation, and worker restart leave safe durable states;
- retranscription preserves the current transcript until successful completion;
- canonical lesson IDs remain stable after media path changes;
- playback activity gates background work through the existing resource manager;
- transcript panel seeking, highlighting, search, and keyboard access work from observable behavior;
- all remaining tests pass, typecheck passes, and lint/build results are reported accurately.
