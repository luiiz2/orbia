# Orbia v0.8 Connected Library Architecture and Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL after explicit approval: use `superpowers:subagent-driven-development` for independent phases or `superpowers:executing-plans` for sequential phases. Every implementation phase must use checkbox tracking, focused tests, review, and a fresh integration gate.

**Goal:** Decouple canonical learning content from physical and remote media locations so one lesson can use local, removable, Google Drive, or managed offline copies without duplicating progress, notes, history, or organization.

**Architecture:** Canonical course/module/lesson/resource records remain stable in the Vault SQLite database. A new source layer inventories provider items and links one or more physical copies to canonical items; Main-process adapters, synchronization, source resolution, streaming, and offline jobs hide provider details from the renderer.

**Tech Stack:** Electron 39, React 19, TypeScript 5.9, Node.js standard APIs, better-sqlite3, Vite, Zustand, Vitest, existing FFmpeg/optimizer infrastructure, Google Drive REST API v3.

**Spec:** User-provided Orbia v0.8 Connected Library PART 1 and PART 2, requirements 1–100.

## Global Constraints

- No source file may be renamed, moved, overwritten, or deleted without preview, approval, journaled execution, and recovery.
- Cache files are app-owned copies, but removal and relocation still require strict path validation and journaled state transitions.
- Canonical IDs and all learning, Studio, Discovery, profile, theme, collection, and optimization data must survive migration unchanged.
- Google Drive is read-only; provider writes are outside v0.8.
- One Google account may be active at a time; disconnected-account source records remain in the Vault database.
- Provider credentials, authorization headers, remote URLs, and raw filesystem paths remain in the Main process.
- No OneDrive, NAS, or simultaneous multi-account behavior is introduced in v0.8.
- Reuse scanner, parser, import preview, media protocol, optimizer, queue, validator, journal, and resource-management modules through targeted seams.
- Every phase ends with focused tests, `npm run typecheck`, and `npm run lint`; cross-cutting gates also run `npx vitest run` and `npm run build`.
- No implementation begins before explicit user approval of this architecture.

## 1. Current Canonical Media Architecture

`courses`, `modules`, `lessons`, and `content_resources` are the canonical content records. Progress, notes, bookmarks, flashcards, history, goals, Discovery relationships, collections, and Library Studio appearances reference their stable IDs. The v0.8 source layer must link to these records; it must not replace or recreate them.

Library Studio is already the correct logical-organization seam: `library_appearances` stores custom title, parent appearance, section, order, tags, metadata, reference, and hidden state independently from physical paths. Synchronization must never rewrite those fields.

## 2. Current Path and Source Representation

Canonical rows still contain physical locators:

- `courses.root_path` and `courses.source_type`;
- `modules.folder_path`;
- `lessons.file_path`, filename, size, availability, hash, and fingerprint;
- `content_resources.file_path`.

`ContentSource` in `src/types/course.ts` is a shallow, unused type. Existing availability values describe storage form rather than operational state. v0.8 should replace that conceptual model with explicit source records and states while retaining legacy columns as compatibility projections during migration.

## 3. Current Scanner, Importer, and Watcher Architecture

The current safe import flow is:

`native picker → opaque capability → ImportSessionService → ScannerService → ParserService → path-free preview → approval → CourseImportService → journal → database transaction`.

The scanner is read-only, recursive, skips symlinks/non-regular files, records metadata and sampled fingerprints, and preserves non-media resources. The parser already handles hierarchy, natural sort, title cleaning, sidecars, materials, and duplicate candidates without silently deleting them.

No filesystem watcher, mount watcher, incremental reconciliation loop, stable removable-volume identity, or periodic verification currently exists. Watcher events must therefore be added as hints into a new sync module, not embedded into ScannerService.

## 4. Current v0.7 Stream Abstraction

`MediaSourceInput` provides metadata, a `Readable`, an optional local path, and a direct-file capability. `LocalFileSourceInput`, `StreamSourceInput`, and `RemoteStreamSourceAdapter` already exist. `TranscodingEngineService` pipes non-direct inputs into FFmpeg through `pipe:0`.

The gap is orchestration: the optimizer worker always checks `fs.existsSync(job.sourcePath)` and creates `LocalFileSourceInput`. Remote input is therefore structurally anticipated but not reachable through the persistent queue.

## 5. Current v0.7 Compact-Output Architecture

The optimizer already provides metadata analysis, hardware selection, planning, stream transcoding, validation, backups, atomic replacement, provenance, exclusions, persistent jobs, recovery, retries, progress events, and basic resource controls.

Its final action replaces a local original. Offline Drive assets need a sibling terminal action: validate the output, register it as a managed offline source, and leave the original Drive source and canonical lesson untouched.

## 6. Current Player Source Interface

`VideoPlayer` builds `media://` directly from `activeLesson.filePath`. The protocol validates an absolute path, authorizes it against exact registered paths, checks the local filesystem, and serves one byte range with HTTP 206. A playback error marks the lesson broken; no source fallback exists.

The player controls, progress store, saved-position logic, notes, bookmarks, and queue should remain. Only source acquisition changes from `lesson.filePath` to an opaque playback session resolved in Main.

## 7. Current Background Queue Infrastructure

`optimization_queue`, `OptimizationQueueService`, and `OptimizationWorkerService` provide persistent state, startup recovery, pause/resume/cancel/retry, progress, temporary output cleanup, and three-attempt review escalation. The worker starts during IPC registration and waits for an open Vault.

The queue is optimizer-specific, local-path-specific, and has no delayed retry timestamp or network error classes. It should be extended through typed job kinds and a media-input factory rather than replaced by a second independent queue framework.

## 10. Generic Content Source Architecture

Create `src/types/source.ts` and `src/main/services/sources/` with these core terms:

```ts
export type SourceProvider = 'local-folder' | 'removable' | 'google-drive' | 'managed-offline'

export type SourceAvailability =
  | 'available'
  | 'offline'
  | 'disconnected'
  | 'auth-required'
  | 'missing'
  | 'syncing'
  | 'error'
  | 'relink-required'

export interface SourceAdapter {
  identifyRoot(locator: SourceRootLocator): Promise<SourceRootIdentity>
  reconcile(request: ReconcileRequest): AsyncIterable<SourceChangeBatch>
  open(item: SourceItemLocator, range?: ByteRange): Promise<SourceReadHandle>
  probe(item: SourceItemLocator): Promise<SourceTechnicalMetadata>
  watch?(root: SourceRootLocator, onDirty: (hint: DirtyHint) => void): Promise<Disposable>
}
```

`SourceManagerService` owns adapter registration, source/root lifecycle, summaries, and Sync Now. `SourceSyncService` consumes normalized changes. `SourceResolverService` selects playback sources. Provider-specific code remains inside adapters.

## 11. Proposed Database Migration

Add migration `007_v08_connected_library` to the Vault database with:

- `content_sources`: user-visible source definition, provider, display name, account reference, effective status, preference weight, timestamps.
- `source_roots`: monitored root, provider root ID, stable device ID, mount hint, relative base, sync cursor/corpus, sync status, last sync/verification, provider config JSON.
- `source_items`: provider item ID, source root, relative path, untrusted physical name, MIME type, size, revision, checksum/fingerprint, duration/resolution, availability, technical metadata.
- `canonical_source_links`: source item linked to exactly one lesson or content resource, manual-link flag, per-item preference, timestamps. A source item may link to separate canonical lessons only through explicit or course-scoped decisions.
- `source_match_candidates`: source item, candidate canonical item, confidence, evidence JSON, review status, decision timestamp.
- `offline_assets`: managed source item, original source item, asset ID/path, pin state, policy reason, codec, resolution, size, optimizer profile, validation and access timestamps.
- `source_sync_runs`: source root, cursor before/after, status, counts, start/end timestamps, sanitized error.

Add `provider_accounts` to the global Config database: provider, stable account subject, display identity, encrypted refresh token blob, granted scopes, active flag, status, and timestamps. Multiple known identities may remain, but a unique constraint permits only one active Google account.

Migration procedure:

1. Create a SQLite backup before schema mutation.
2. Begin one Vault transaction and create source tables/indexes.
3. Create one managed-vault source/root and conservative local-reference roots without guessing common parents.
4. Backfill every existing lesson and content resource path into a source item and canonical link, including unavailable paths.
5. Preserve all canonical IDs and legacy path columns.
6. Assert canonical row counts and ID sets are unchanged, every non-empty legacy path has a link, and `foreign_key_check` is empty.
7. Commit only after all assertions pass; otherwise rollback and retain the backup.

Legacy path columns remain readable projections throughout v0.8 and are updated transactionally for local compatibility. Their removal is not part of v0.8.

## 12. Local Source Adapter

`LocalFolderSourceAdapter` uses `ScannerService` for initial inventory and targeted subtree scans. Persist source-relative paths and stable file identity where the platform exposes it; treat absolute mount paths as runtime hints.

`fs.watch({ recursive: true })` may emit dirty hints. Debounce by root/subtree, reconcile against persisted source items, and classify actual changes only after stat/inventory comparison. Unsupported or unreliable watcher behavior falls back to lightweight scheduled verification without adding a new dependency.

## 13. Removable-Drive Identity and Remapping

Create a platform seam `VolumeIdentityAdapter`. Windows uses a fixed, argument-safe native probe for volume identity; macOS/Linux implementations use equivalent read-only platform metadata. Never construct shell commands from remote or user-controlled filenames.

Automatic remap requires the same stable volume ID plus the known source-root identity. Matching folder shape alone is never high confidence. If stable identity is unavailable or conflicts, mark `relink-required` and ask the user. Managed cache roots additionally carry an app-owned manifest with cache ID and Vault ID.

## 14. Google Drive Authentication

Use a Desktop OAuth client, the system browser, a loopback listener bound to `127.0.0.1` on a random port, PKCE S256, cryptographic `state`, exact redirect validation, a short timeout, and one callback consumption. Do not use an embedded login window or manual copy/paste flow.

Privileged auth and Drive calls stay in Main. Persist only the refresh token, encrypted with Electron `safeStorage`; access tokens remain in memory. On Linux, reject persistent connection when the selected backend is insecure rather than storing recoverable plaintext. Never log token responses, authorization headers, or callback query strings.

Use the narrowest scope that can recursively list and download user-selected trees. Because metadata-only scope cannot stream bytes and `drive.file` may not expose arbitrary selected descendants, treat `drive.readonly` and its Google verification/security-assessment implications as a P0 product gate.

Official references: [Google desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), and [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).

## 15. Drive Folder and Root Model

Each selected folder becomes `source_roots` data with stable folder ID, account reference, Drive corpus/shared-drive ID when applicable, user-visible path snapshot, and sync cursor. Folder names are display metadata, not identity.

Initial enumeration traverses only selected roots, requests minimal fields, follows pagination, and stores parent relationships needed to decide whether later changes remain inside a monitored tree. No full-account scan is allowed.

## 16. Drive Incremental Synchronization

Persist `changes.getStartPageToken` and consume `changes.list` pages until `newStartPageToken`, committing cursor and normalized changes together. Maintain cursors per relevant corpus/shared drive. A change record is current state, so compare it to persisted `source_items` rather than assuming it is a property delta.

Filter account-wide changes through the stored selected-root ancestry graph. A moved item with the same provider ID updates its source locator. Removed or inaccessible items remove availability of that source only. An expired/invalid cursor schedules a targeted selected-root rebuild, not a full Drive rescan.

Use bounded retries with jittered exponential backoff for 429, retryable 403, and 5xx responses. Authentication, permission loss, deletion, and malformed requests are non-retry-equivalent error classes. Official references: [Drive changes](https://developers.google.com/workspace/drive/api/guides/manage-changes) and [Drive error handling](https://developers.google.com/workspace/drive/api/guides/handle-errors).

## 17. First-Import Preview

Generalize the existing import-session repository so Drive sessions are durable. A Drive scan feeds provider-neutral scanned entries into the current parser and preview contracts. Persist session state and proposal ownership, but do not insert canonical entities, source links, or valid offline assets before approval.

Commit applies user title/hierarchy corrections in one database transaction, links high-confidence existing canonical media, stores medium-confidence candidates for review, and creates new canonical records only for approved unmatched content. Cancel deletes only session state and app-owned temporary data.

The existing raw multi-course/import-batch path must be routed through this session boundary before it is reused for Drive.

## 18. Source Equivalence and Matching

Create a pure `SourceMatcher` with ordered evidence:

1. Stable provider item ID means the same source item after rename/move.
2. Same canonical course context is required for automatic canonical linking.
3. Provider checksum or matching sampled fingerprint plus compatible metadata may produce high confidence.
4. Normalized title, relative structure, duration, size, resolution, codec, and filename contribute layered evidence.
5. A remote sampled fingerprint is fetched with small head/tail ranges only when cheaper evidence remains ambiguous.
6. Equal size/duration alone is medium confidence, not automatic linking.
7. Cross-course hash equality produces an informational duplicate signal only.

Persist evidence and threshold version with every candidate. High confidence auto-links; medium queues review; low stays separate. Manual Link as Another Source and Unlink Source update only source links, never provider files.

## 19. Source Resolver and Scoring

Resolution has two stages:

1. Eligibility gate: availability, authentication, playability, range capability, provider permission, and temporary circuit-breaker state.
2. Centralized score: quality, locality, latency EWMA, throughput EWMA, stability, offline readiness, decayed failures, and preferred-source bonus.

Keep constants in `src/main/services/sources/source-score.config.ts`. A preference is a bonus, never an eligibility override. Return an explanation vector for advanced details while normal playback receives only the selected source/session.

Do not perform provider requests while rendering cards. Resolver inputs come from cached SQLite metadata and health summaries; live checks occur only at playback preparation or explicit Sync Now.

## 20. Playback Fallback

`player:prepare-playback(lessonId, sourceOverride?)` returns an opaque session ID, `media://playback/<sessionId>`, selected-source summary, and seek capability. Main stores the session/source binding with expiry.

On startup/open failure, report a classified source failure, exclude it for the current resolution attempt, and resolve another source. On mid-playback error, save current position, create a replacement session, swap the media URL, and seek after metadata/canplay. Existing progress remains canonical and is never reset.

Manual Play From applies to the current playback by default. A separate explicit preference action persists a scoring bonus without disabling fallback.

## 21. Remote Streaming

Extend the protocol with an opaque playback route while retaining the legacy local-path route during migration. The protocol asks the playback-session module for a `SourceReadHandle` containing status, MIME type, total size, optional content range, seekability, and a bounded `Readable`.

The Drive adapter calls `files.get?alt=media`, forwards one validated `Range` header, checks `capabilities.canDownload`, and returns real 200/206/416 semantics. Tokens and provider URLs never enter the renderer or media URL. If a source cannot seek, omit `Accept-Ranges` and disable seek honestly.

Streaming uses Node backpressure and a bounded in-memory high-water mark; it does not become an offline cache. Official reference: [Drive download and byte ranges](https://developers.google.com/workspace/drive/api/guides/manage-downloads).

## 22. Offline Download and v0.7 Integration

Extend `optimization_queue` compatibly with typed job kind, source item/link ID, operation stage, next-attempt timestamp, and network error class. Existing local optimizer rows remain valid. Replace the worker's unconditional local-file check with a `MediaSourceInputFactory`:

- local source → `LocalFileSourceInput`;
- remote progressive source → `RemoteStreamSourceAdapter`;
- remote fallback → app-owned staged local input.

Pipeline:

`queued → connecting → streaming/transcoding → validating → registering-source → completed`.

The existing planner avoids unnecessary encoding. Progressive FFmpeg input is attempted first. A classified progressive failure may download the complete temporary original, transcode, validate, register the compact source, and then remove only the temporary original. Failed or partial output never becomes a valid source.

## 23. Cache Management

Store cache location and size policy in global settings; keep per-asset state in the Vault database. Default to an app-owned location partitioned by Vault ID. Name files by internal asset ID plus validated extension, never by raw remote filename.

Eviction ordering is a deterministic query that protects pinned assets, then prefers in-progress, next lessons, recent downloads, My List, and recent access. It prefers evicting completed/old items with another available source. Pinned assets are an absolute exclusion.

Eviction first renames the asset into an app-owned same-volume quarantine, then transactionally removes the managed source link and completes the journal. Final purge happens after a grace period. Cache relocation is a resumable job: copy, validate, register destination, switch links, quarantine old copy, then purge.

## 24. Source Health

Track compact per-source-item health: last success/failure, consecutive failures, latency/throughput EWMA, last error class, and temporary blocked-until timestamp. Provider-wide auth/account state remains on the source definition.

Failures decay by age and successes recover health. A transient network error cannot permanently punish a source. Corruption or permission denial has a stronger, separately classified effect. Health writes are batched/throttled to avoid SQLite churn during playback.

## 25. Organization Protection

Synchronization may update source items, provider names, locators, availability, size, duration, resolution, checksum, revision, and technical metadata. It must not update canonical titles, module IDs, appearance parentage, section IDs, display order, tags, references, custom metadata, or themes.

Known provider moves update `source_items` only. New unplaced source items enter review/import placement. Existing `identity-resolver` evidence may be reused, but its current behavior that moves a lesson's canonical `module_id` must not be reused by the sync engine.

## 26. Security Risks and Controls

- OAuth interception: loopback-only binding, PKCE, state, timeout, single-use callback.
- Token disclosure: Main-only token store, `safeStorage`, redacted structured logging, no renderer token/URL.
- Remote path traversal: internal asset IDs, canonicalized cache roots, strict containment checks, no remote-name path composition.
- Shell injection: no shell-built commands; platform probes receive validated fixed arguments.
- Protocol widening: opaque playback sessions authorize exact canonical/source IDs; the protocol is not a generic HTTP proxy.
- Redirect leakage: Drive client strips authorization on cross-origin redirects and accepts only expected Google endpoints.
- Untrusted media metadata: validate sizes, MIME/extension, ranges, integer bounds, and response lengths.
- Existing hardening debt: `sandbox: false` and unrestricted `setWindowOpenHandler` should be addressed in a focused security phase if compatibility tests permit.

## 27. Data-Loss Risks and Controls

- Migration partial backfill: backup, one transaction, ID/count/link/FK assertions, legacy columns retained.
- False automatic linking: high-confidence threshold requires strong evidence and course boundary.
- False drive remap: stable volume identity required; ambiguity becomes review.
- Sync overwriting Studio: source-only mutation contract plus regression tests.
- Remote deletion/account switch: remove availability/link only; never cascade canonical data.
- Cache failure: temporary files are invalid until validation and registration commit.
- Cache eviction/relocation: containment checks, pin gate, journal, quarantine, resumable state.
- Unlink vs delete confusion: Unlink Source is always logical; physical deletion is a separate explicit action and unavailable for Drive.

## 28. Privacy Risks and Controls

- Drive metadata and selected-root inventory remain local in the Vault database.
- No telemetry, analytics upload, or cloud-side hashes are added.
- Only selected Drive trees are indexed; account-wide change entries are filtered locally and not rendered indiscriminately.
- Access tokens remain memory-only; refresh tokens are encrypted at rest.
- Logs exclude tokens, authorization headers, callback URLs, full remote metadata payloads, and sensitive query parameters.
- Offline media is stored as ordinary local media and is not encrypted by default; the UI must disclose the selected cache location and storage behavior.

## 29. Performance and API-Quota Risks

- Avoid full Drive rescans through persisted change cursors and targeted selected-root rebuilds.
- Request minimal Drive fields, paginate, batch metadata operations where supported, and limit concurrent network calls.
- Use bounded jittered backoff and a provider circuit breaker to prevent retry storms.
- Coalesce watcher events and run targeted reconciliation.
- Add indexes for source root/item IDs, relative paths, canonical links, availability, candidates, sync status, and offline eviction ordering.
- Return library/source summaries through one batched IPC query; never one request per card or file.
- Cache source-summary projections in Main and invalidate them transactionally after source changes.
- Keep playback scoring limited to one lesson and cached candidates.
